# pispot

A Raspberry Pi 5 Wi-Fi hotspot and router with a live web dashboard.
The Pi shares an upstream Wi-Fi connection (USB adapter on `wlan1`) to
clients connected to its built-in hotspot (`wlan0`), with a browser-based
dashboard for monitoring and control.

## What it does

- **Live dashboard** — interface throughput, hotspot clients, WAN link
  status, admin/backup interface, system load/memory/temperature
- **WAN control** — WAN Up / WAN Down buttons start and stop the upstream
  wpa\_supplicant connection
- **WiFi network management** — add, remove, and apply WAN networks through
  the browser without touching the Pi
- **Role-based access** — read-only and admin roles via Unix groups and PAM;
  credentials sent over HTTPS with Basic Auth
- **HTTPS only** — TLS terminated in the dashboard container; cert and key
  mounted from the host

## Hardware

| Component | Role |
|---|---|
| Raspberry Pi 5 | Host |
| Built-in `wlan0` | Hotspot / LAN (AP mode, `10.10.10.1/24`) |
| USB Wi-Fi adapter `wlan1` | WAN uplink (station mode) |
| Ethernet `eth0` | Admin / backup WAN |

> Only the Raspberry Pi 5 has been tested. Other models are not supported.

## Architecture

```
clients ──── wlan0 (hostapd + dnsmasq)
                │
              Pi 5
                │
             wlan1 ──── upstream AP
             eth0  ──── admin network

┌────────────────────────────────────────┐
│  Docker container: pispot-ui           │
│  Go HTTP server, :443 HTTPS            │
│  reads /proc, /sys, dnsmasq leases     │
│  talks to pispot-authd via Unix socket │
└────────────────────────────────────────┘
                │ /run/pispot/pispot-authd.sock
┌────────────────────────────────────────┐
│  systemd service: pispot-authd (root)  │
│  PAM authentication via pamtester      │
│  WAN control via systemctl + dhcpcd    │
│  WiFi config via wpa_supplicant conf   │
└────────────────────────────────────────┘
```

**pispot-ui** runs in Docker with host networking and a read-only rootfs.
It never runs as root and has no write access to the host.

**pispot-authd** runs as a native systemd service with root privileges.
It is the only component that touches wpa\_supplicant, dhcpcd, and PAM.
The dashboard delegates all privileged operations to it over a Unix socket.

## Prerequisites

**Mac (build machine):**
- Go 1.26+
- Docker Desktop (arm64 image builds require no emulation on Apple Silicon)
- Ansible (`pip install ansible` or `brew install ansible`)
- Python 3.9+
- Node.js (for `make js-check`)

**Raspberry Pi 5:**
- **Raspberry Pi OS Lite (64-bit)** — no desktop, minimal footprint.
  Flash with [Raspberry Pi Imager](https://www.raspberrypi.com/software/).
- Docker 29+
- `pamtester` (installed by `make setup`)

## First-time setup

### 1. Prepare the Pi

1. Flash **Raspberry Pi OS Lite (64-bit)** to a new SD card using Raspberry Pi Imager
2. In Imager's **Edit Settings** before writing:
   - Set the hostname
   - Enable SSH
   - Create your user account and password
3. Boot the Pi. If you set up password-only auth, copy your SSH key:
   ```sh
   ssh-copy-id <user>@<hostname>.local
   ```
4. Confirm SSH access before proceeding:
   ```sh
   ssh <user>@<hostname>.local
   ```
5. Note the hostname and username — you will enter both in `make init`

### 2. Clone and configure

```sh
git clone https://github.com/mcs-net/pispot
cd pispot
make init
```

The wizard prompts for Pi hostname, SSH user, dashboard title, TLS cert
name, HTTPS hostname, Wi-Fi country, hotspot credentials, and WAN network
credentials. It writes three gitignored files:

- `dashboard/.env` — Pi hostname, cert name, dashboard title
- `ansible/inventory/hosts` — Ansible inventory
- `ansible/group_vars/all.yml` — all site-specific variables

Re-running `make init` pre-populates every prompt with the saved value;
press Enter to keep it unchanged.

### 3. TLS certificate

Place your certificate files in `ssl/` using the cert name you chose:

```
ssl/<cert-name>.crt    certificate
ssl/<cert-name>.key    private key
ssl/<cert-name>.ca     CA/intermediate bundle
```

For local testing, generate a self-signed cert instead:

```sh
make gen-certs
# then set PISPOT_TLS_CERT_NAME=test_cert in dashboard/.env
```

To install a renewed cert later, replace the files in `ssl/` under the same
name and run `make deploy-cert`. It checks the files first, changes nothing
else on the Pi, and confirms the dashboard is serving the new cert.

### 4. Build

```sh
make build          # compile pispot-authd, pispotctl (linux/arm64)
make docker-build   # build pispot-ui Docker image (linux/arm64)
```

### 5. Bootstrap the Pi (first time only)

```sh
make bootstrap      # apt upgrade, install packages, Docker, set Wi-Fi country
```

> When prompted `BECOME password:`, enter the sudo password for your Pi user account.

This installs Docker from the official Docker apt repository and adds your
user to the `docker` group. The Pi reboots if required — the reboot also
ensures the new group membership is active for subsequent steps.

### 6. Deploy

```sh
make deploy-all
```

> When prompted `BECOME password:`, enter the sudo password for your Pi user account.

This will:
1. Build host binaries (`pispot-authd`, `pispotctl`)
2. Run Ansible `pi-setup.yml` — creates pispot Unix groups, adds your user
   to all three, configures dhcpcd, hostapd, dnsmasq, nftables, avahi,
   installs pispot-authd and pispotctl, deploys TLS certs
3. Build the Docker image and ship it to the Pi
4. Start the dashboard container

A confirmation prompt is shown before proceeding, as the deploy restarts
all services and briefly disconnects active dashboard users.

## Day-to-day operations

```sh
make deploy-dashboard   # rebuild and redeploy the dashboard only
make deploy-authd       # rebuild and redeploy pispot-authd + pispotctl only
make deploy-cert        # install renewed TLS cert from ssl/, restart dashboard
make checkup            # read-only Ansible health check
make logs               # ssh to Pi and run pispotctl logs
make ssh                # open an SSH session to the Pi
```

> `deploy-authd`, `deploy-cert` and `checkup` run Ansible and will prompt `BECOME password:` —
> enter the sudo password for your Pi user account.

## Upgrading the Pi

Always run upgrades inside `tmux`. Network connections to the Pi can drop
during an upgrade, especially over the hotspot, and an upgrade running in a
plain SSH session could be interrupted partway through. `make bootstrap`
installs `tmux`; on a Pi bootstrapped before it was added, run
`sudo apt install tmux`.

Start the session, or rejoin it after a disconnect, with the same command:

```sh
tmux new -A -s upgrade
```

Then, inside the session:

```sh
sudo apt update
apt list --upgradable
sudo apt -o Dpkg::Options::=--force-confdef -o Dpkg::Options::=--force-confold full-upgrade
```

The `force-conf` options keep existing config files, so package defaults
don't replace the ones set up by `pi-setup.yml`.

Reboot once the upgrade has finished. A `tmux` session doesn't survive a
reboot, so start a new one for any later work.

## User accounts and access

Three Unix groups control access. They're levels, lowest first:

| Group | Level | Permissions |
|---|---|---|
| `pispot-ro` | read-only | view dashboard, no controls |
| `pispot-admin` | admin | full dashboard, WAN up/down, WiFi config, Logs, Users |
| `pispot-owner` | owner | same as admin, can't be changed from the dashboard, and gets SSH and `sudo` |

An account can't be in a group without being in every lower one, so it's in
one, two or all three of them. A group doesn't count if a lower one is missing:
an account in `pispot-admin` but not `pispot-ro` can't log in, and one in
`pispot-ro` and `pispot-owner` but not `pispot-admin` is only read-only. It
still can't be changed from the Users tab, since being in `pispot-owner` is
enough.

Only owners get `sudo`, from `/etc/sudoers.d/pispot`. Admins don't need it,
because dashboard actions go through `pispot-authd`, which runs as root and only
does the jobs the page offers. It's also why the Admin checkbox on the Users tab
can't grant root. An account can also have `sudo` from elsewhere, such as the
`sudo` group, so one that's in both has a harmless duplicate.

Only owners get SSH among accounts in these groups, from
`/etc/ssh/sshd_config.d/pispot.conf`. Everyone else in them is refused, even with
the right password. New accounts from the Users tab also have no login shell,
but that alone wouldn't be enough, because a tunnel (`ssh -N -L`) doesn't need
one. Accounts outside these groups aren't affected.

The health summary on the Logs tab warns if an owner can't use `sudo`, if anyone
else in these groups can, if an account breaks the level rule above, or if either
of those two files is missing. It asks `sudo` itself rather than reading the
config, so it holds however access was granted.

All three groups and both files are created automatically by `make setup`.
The user you entered in `make init` is automatically added to all three on first
deploy.

Admins can manage users on the dashboard's Users tab, or on the Pi:

```sh
sudo useradd -m alice
sudo passwd alice
sudo usermod -aG pispot-ro alice                           # read-only
sudo usermod -aG pispot-ro,pispot-admin alice              # or admin
sudo usermod -aG pispot-ro,pispot-admin,pispot-owner alice # or owner
```

To upgrade an existing Pi, create the new group and add your account to all
three **before** installing the new `pispot-authd`. If you install it first, the
Users tab won't work and any account missing `pispot-ro` can't log in to the
dashboard:

```sh
sudo groupadd pispot-owner
sudo usermod -aG pispot-ro,pispot-admin,pispot-owner "$USER"
```

Then add the sudoers file by copying `host/files/pispot.sudoers` to the Pi as
`/tmp/pispot.sudoers` and installing it. `visudo` checks it first, because a
broken sudoers file can stop `sudo` working altogether:

```sh
sudo visudo -cf /tmp/pispot.sudoers && \
  sudo install -o root -g root -m 0440 /tmp/pispot.sudoers /etc/sudoers.d/pispot
rm /tmp/pispot.sudoers
```

Add the SSH rule the same way, from `host/files/pispot-sshd.conf`. Keep your SSH
session open until a new login works, in case the rule locks you out:

```sh
sudo /usr/sbin/sshd -t -f /tmp/pispot-sshd.conf && \
  sudo install -o root -g root -m 0644 /tmp/pispot-sshd.conf /etc/ssh/sshd_config.d/pispot.conf && \
  sudo /usr/sbin/sshd -t && sudo systemctl reload ssh
rm /tmp/pispot-sshd.conf
```

Credentials are validated via PAM on each login (cached for 5 minutes).

## Dashboard tabs

| Tab | Contents | Who sees it |
|---|---|---|
| Networking | Interfaces, hotspot clients, WAN, system | All logins |
| Power | Epic PWRgate, grayed out unless it's on USB | All logins |
| Logs | Health summary, system details and service logs | `pispot-admin` only |
| Users | List accounts, and add, change and delete non-owners | `pispot-admin` only |

The Logs tab is read-only and shows the output of a fixed list of commands in
`host/internal/diag/diag.go`. It never reads the Wi-Fi configs or TLS private
keys, and its output also passes through a redaction filter. When adding a
source, keep secrets out of it: the filter is only a second layer.

The Users tab manages only human accounts (UIDs 1000 to 59999) in `pispot-ro`
and not in `pispot-owner`. New accounts always join `pispot-ro`, and
`pispot-admin` is an optional extra on top. The page lists owners too, but can't
add anyone to `pispot-owner` or change an owner in any way, which keeps the
account from `make init` out of reach. Manage owners over SSH. They can still
use the page to manage everyone else.

You can't delete your own account or remove your own admin access. New
accounts get no shell, so they can log in to the dashboard but not SSH.
Deleting an account keeps its home folder.

## pispotctl

The `pispotctl` tool is installed at `/usr/local/bin/pispotctl` on the Pi
and requires root for all commands.

```sh
sudo pispotctl wan-up        # start wpa_supplicant@wlan1 + request DHCP
sudo pispotctl wan-down      # stop wpa_supplicant@wlan1 + release DHCP
sudo pispotctl status        # show service states and network info
sudo pispotctl wifi list     # list configured WAN networks (passwords masked)
sudo pispotctl logs          # dump all pispot-related logs
```

## Dashboard environment variables

These are set in `dashboard/docker-compose.yml` and sourced from
`dashboard/.env`. The `.env` file is generated by `make init`.

| Variable | Default | Description |
|---|---|---|
| `LISTEN_ADDR` | `:443` | Listen address |
| `TLS_CERT_FILE` | | Path to fullchain.pem inside container |
| `TLS_KEY_FILE` | | Path to private key inside container |
| `REQUIRE_TLS` | `true` | Reject non-TLS starts |
| `AUTH_SOCKET` | | Unix socket path to pispot-authd |
| `AUTH_REALM` | `pispot` | HTTP Basic Auth realm |
| `DASHBOARD_TITLE` | `pispot` | Page title and header text |
| `HOTSPOT_IF` | `wlan0` | LAN / AP interface |
| `WAN_IF` | `wlan1` | WAN / upstream interface |
| `ADMIN_IF` | `eth0` | Admin / backup WAN interface |
| `PROC_PATH` | `/host/proc` | Host /proc mount point |
| `SYS_PATH` | `/host/sys` | Host /sys mount point |
| `LEASES_PATH` | `/host/dnsmasq.leases` | dnsmasq lease file |
